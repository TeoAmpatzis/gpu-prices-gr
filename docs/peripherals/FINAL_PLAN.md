## 2. Architecture
- No database [V]: JSON per category in `public/data/<cat>/`; build writes `list.v2.json`, `detail.json`, builder index + per-slot files, model chunks, manifest, search (`vite-plugin-data.ts`). Storage layout unchanged; monitor adds `public/data/monitor/`.
- Registry fields: `id`, `domain` (`components|peripherals`), names (el/en), icon, search words, `builderSlot?`, `enabled`, `visible`, definition references (filters, specs, comparison). TypeScript predicates/formatters stay in TS; Python source config stays in Python; a test checks category ids and identity fixtures agree across both. No plugin framework, no code generation.
- Phase 1 replaces `SLOT_OF: Record<Category, Slot>` (`src/lib/pick.ts:11`) with `slotOf`; `pick=1` is rejected for non-slot categories before the picker chunk is imported (`CategoryView.tsx:73`); `ModelPage` builder fit stays slot-only. A spike classifies the 21 `Record<Category>` files (generic vs slot-only); presentation maps such as `FILL` (`keySpecs.ts:36`) get monitor entries.
- Scraper: `CATEGORIES` becomes the single list (`glitches.py`, `merge_history.py` import it). A source/category **capability table** distinguishes lists, specs, shipping, history; an unsupported pair is never a failed scrape; `validate_skroutz.py` and the `scrape.yml` "nine categories" gate read the table.
- Navigation: «Εξαρτήματα PC / PC Components», «Περιφερειακά / Peripherals», PC Builder, Compare (only once `/compare` exists). The Peripherals menu item goes straight to Monitors. Mobile: catalogue sheet with both groups. Breadcrumb Home › Peripherals › Monitors. Search includes monitors with a domain tag. No empty future categories anywhere.
- "Supported by code" ≠ "published". Global data guards are never disabled to admit monitors; a monitor-specific initial minimum is added (`MIN_MODELS`).

## 3. Monitor data
**Identity.** A monitor model = one manufacturer model code (MPN) + brand. Stages: normalize (Unicode, Latin/Greek look-alikes, aliases, boilerplate) → extract MPN/GTIN/revision/region → match exact trusted identifiers → exact brand+model variants only when discriminators agree → fuzzy similarity only creates **review candidates** → unresolved listings stay separate/quarantined. Unknown discriminators never bridge two known variants. Suffix equivalence only when documented per maker. Size, panel, refresh mode, connector, revision and materially different bundles stay separate.
**Conflicts.** Conflicting specs under one proven brand+MPN produce **field conflicts**, not automatic identity splits. Split only with evidence of distinct variants. Identity is resolved after enrichment and before identity-dependent outputs are written (`scraper/main.py` order around `:291-303`). Key changes need explicit alias/history migration; an ambiguous split never copies one combined price history into several variants.
**Specs.** Typed `MonitorSpecs` (display, image, gaming, connectivity, physical, power, other) with raw → canonical normalization; unknown = null, never guessed; explicit false, unknown, conflict and not-applicable are distinct. Field evidence states: `stated`, `corroborated`, `derived`, `conflict`, `unknown`. Monitor fields are **not** in `Category.shared`, and `specs.apply` (`scraper/specs.py:417`) and `share_fields` never overwrite them; title/page observations are preserved before resolution.
**Evidence delivery.** Ingestion cache `public/data/monitor/spec_evidence.json` (raw, value, source URL, checkedAt, parser version). A build contract turns observations into resolved values + conflict alternatives + provenance, written to **model chunks** (raw caches are pruned from production, `vite-plugin-data.ts:191`); list payloads carry only the selected values. A parser-version change invalidates cached observations. A test checks every displayed state matches its displayed value.
**Staging.** BestPrice and other sources currently drop records before enrichment (`bestprice.py:29,38`, `main.py:197`). Monitors use a staging/rejection report: listings lacking size or resolution are kept in a rejection file with a reason, never silently discarded, and coverage/recall are measured against it.
**Sources and limits.** Phase 0 recon establishes permitted monitor paths and volumes per source (BestPrice's page limit in code is `MAX_PAGES = 80`; any source-side limit is unverified). No evasion of blocks. Skroutz: lists only (D2). Shipping: Skroutz none; BestPrice per existing product-page logic; e-shop hardcodes shipping 0 above €90 (`shipping.py:159`), so monitor shipping for e-shop stays **unknown** until a monitor-specific rule is verified. Stale shipping (no age limit in `_usable`, `shipping.py:97`) is shown separately via an optional shipping-observed time carried to derived payloads.
**Filters.** Price, brand, size buckets, resolution, refresh threshold, panel, aspect, HDR, adaptive sync, ports (HDMI/DP/USB-C/PD/Thunderbolt/KVM/hub), curvature, response, gamut, VESA/stand. Tri-state yes/no/unknown predicates (current `yesNo` coerces unknown to no, `categoryRules.ts:149`); typed ranges extended through URL state, filtering and facets (`filterUrl.ts:96`), not only `RANGE_FIELDS`. Strict feature filters exclude unknown/conflict; "include unknown" is explicit. Sorts: Best deals, Recommended (transparent popularity/offer coverage, no invented quality score), price, size, refresh (unknowns last, stable ties).
**Pages.** Monitor spec groups with evidence/conflict display, no builder-fit block, Compare button, family/variant links. All strings in Greek and English.

## 4. Universal comparison
- Pure module `src/lib/compare/` (lazy chunk), independent of `src/engine/`, no pricing maths of its own. Definitions are typed TS objects: id, el/en label, group, accessor, kind, canonical unit, equality rule, applicability, formatter, optional preference direction (default none).
- Reference = `{cat, familySlug, selection?: {source,id}}` using the existing `bd1:` encoding (`productSelection.ts`). Cards add their exact listing; a family page asks for a product when rows are listing-specific. Monitors may reference at model (MPN) level with aggregated offers. Existing categories compare source-selected products with that source's price unless identity across sources is proven.
- **Family-level history/deal statistics** (`deals.ts:98`, `ModelPage.tsx:174`) are labelled "family" or omitted for exact selections.
- Rows: differences highlighted with a non-colour marker; no winner; only price/shipping/delivered total may carry a lower-is-better marker, and only when both totals are known. "Hide identical" hides fully known equal rows; unknown/conflict rows stay; a separate control hides rows unknown everywhere.
- Prices: reuse `ownTotal`, `offerTotal`, `sortOffers`, freshness. Availability is shown only when an availability string was actually collected (`offers.ts:60-66`); absent = unknown/hidden, never "offers exist". Cheapest item offer and cheapest known delivered offer stay distinct; stale shipping is shown separately.
- State: localStorage `bdCompare:v1` (versioned references + harmless display snapshots, try/catch, cross-tab `storage` event, corrupt data tolerated), separate from `pcBuild`. Share URL `/compare?v=1&cat=…&items=…` for the active group only, bounded and validated (duplicates rejected); viewing never overwrites saved groups. `PRIVACY_UPDATED` is in `src/lib/site.ts:15`: privacy text and date are updated in the same change.
- **One build snapshot:** all selected products load against one `builtAt` using the existing expected-build check (`modelData.ts:46,62`); a mismatch gives a whole-table refresh/retry state; single failures keep other columns with retry/remove.
- UI: sticky tray (hidden on `/builder` to avoid stacking with the builder bar; one shell-level offset policy), compare page with sticky labels/headers, remove/replace/clear-group; phones show two columns at a time with a product selector.

## 7. Acceptance criteria
- **Classification:** exactly ten published categories; monitor only under peripherals; zero monitor engine parts or builder slots.
- **Matching:** reviewed corpus ≥300 listings (≥100 true matches, ≥100 hard negatives incl. size/panel/refresh/connector/revision variants); zero false merges; ≥95% recall among identifiable positives; unknown identity never bridges variants; normalization and settle twice = once; Python/TS identity outputs agree.
- **Coverage:** ≥90% of launched monitor products have evidenced diagonal, pixel resolution, panel and native refresh, with provenance; measured against a frozen sample of raw eligible source listings **including normalization rejects**.
- **Source policy:** zero requests to disabled monitor operations (Skroutz shipping/specs/history, scheduled runs included); no unapproved Skroutz budget increase; unsupported source/category pairs never appear as failures.
- **Evidence:** every displayed spec state matches its displayed value; conflicts preserved; parser-version invalidation tested.
- **Filters/sort/search:** UI results and facet counts equal an independent oracle including boundaries and unknown policy; URL round trip; stable ties; unknowns last.
- **Pricing:** comparison and product summaries agree to €0.01; unknown shipping, stale shipping, changing prices and absent availability covered.
- **Comparison:** all ten categories render; mixed categories impossible; units/booleans/conflicts/missing handled; persistence (reload, cross-tab, malformed, blocked storage, shared URL, removal, deployment mismatch) passes; family-level history labelled.
- **UI/accessibility:** Greek and English at 360/390/768/1024/1440 px, no overflow, no obscured controls, keyboard operable, non-colour difference markers.
- **Performance** (conditions fixed in Phase 0): tray ≤3 KiB gz initial JS; compare table lazy; 0 monitor requests on initial builder load; existing ≤40 KiB model-chunk and ≤8 KiB builder-index ceilings kept; no main-thread task >50 ms and p95 filter <200 ms on a 5,000-listing fixture.
- **Regression:** existing category prices, grouping keys, URLs, builder selections and engine scenario results unchanged on frozen inputs.

## 8. Risks
Riskiest assumption (Codex): source titles plus the unchanged BestPrice enrichment budget may not give enough reliable manufacturer-code evidence for ≥95% recall and ≥90% coverage without false merges. Phase 0 recon decides this; if it fails, the plan lowers coverage targets or adds maker-site parsers **before** launch rather than loosening matching. Others: source blocks (skip the source), phone Lighthouse score with more filters, photo-repo size, scope creep (deferred: reviews, scores, alerts, accounts, server API, mixed compare table, builder totals).
